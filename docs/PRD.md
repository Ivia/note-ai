## 1. 产品背景与定位

### 1.1 背景
小红书创作者有三个高频痛点：
- **新手起号不知从何开始**：不会选赛道、不会对标、不会定位；
- **老玩家撞到瓶颈**：不清楚自己内容问题在哪；
- **单篇创作耗时长**：标题、正文、标签、配图思路样样要琢磨。

市面上通用 AI 工具（ChatGPT、Claude 原生）对小白门槛太高：要科学上网、要写提示词、要会组合工具。

### 1.2 产品定位
**面向小白的小红书爆款笔记 AI 生成器。** 用户只做"选"和"填"，工具替他完成所有专业创作步骤。

一句话：**把小红书创作专家的工作流，封装成 3 个按钮。**

### 1.3 产品原则
1. **傻瓜式**：用户不配置、不写提示词、不折腾。
2. **零感知后端**：用户侧体验是"打开网页就能用"，背后 Serverless 运维近零。
3. **场景驱动**：只做三个典型场景，不做通用 Chat。
4. **合规优先**：明确免责、尊重原创、不鼓励洗稿。

## 2. 目标用户

| 画像 | 特征 | 诉求 |
| --- | --- | --- |
| **P1：小白起号用户** | 0–100 粉，想做垂类但不知从何下手 | 方向对标 + 起号规划 + 前 5 篇内容 |
| **P2：瓶颈期创作者** | 已发 >10 篇，数据不理想 | 内容诊断 + 风格调优 + 选题池 |
| **P3：单篇灵感用户** | 有主题没灵感，或想抄爆款结构 | 主题+卖点 → 完整文案+配图思路 |

**共同特征**：不懂技术、不会配环境、愿意为好用的工具付费、希望即开即用。

### 4.2 场景一：新手起号助手

**平台限制说明**：本地自用版无后端，不支持自动抓取小红书数据，对标内容由用户手动粘贴。移动端不支持，桌面端专用。

**用户流程**
1. 进入「起号助手」Tab，查看起号记录列表
2. 点击「新起号」按钮，弹出左右分栏弹窗
3. 左侧填写：垂类方向 / 个人定位标签 / 起号目标 / 对标参考笔记（可选粘贴文本）
4. 点击「一键生成」，右侧实时展示生成结果
5. 确认结果后点「保存到历史」，弹窗关闭，列表新增一条记录
6. 点击列表中的记录，进入详情页查看报告并按需生成起号笔记

**输出物**
- **对标分析报告**：共性选题、标题套路、封面风格、互动话术
- **账号定位建议**：切入点、差异化、昵称/简介范例
- **30 天内容节奏表**：每周主题 + 发帖频率
- **起号笔记**（详情页按需生成，可选 1 / 3 / 5 篇）：每篇含标题候选 + 正文 + 话题 + 配图思路

**历史记录策略**
- 与场景三（单篇文案）历史记录**完全分离**，各自独立存储
- 保存内容：方向标签 + 定位 + 目标 + 模型 + 时间 + 完整生成内容（报告 + 节奏表）
- 列表按创建时间倒序排列

**需求优先级**

| 功能点 | 优先级 |
| --- | --- |
| 起号记录列表 + 新起号弹窗 | P0 |
| 对标分析 + 账号定位 + 节奏表生成 | P0 |
| 详情页 + 按需生成起号笔记 | P0 |
| 自动抓取小红书数据 | 暂不做（依赖后端） |

### 4.3 场景二：账号诊断优化

**平台限制说明**：小红书为纯前端渲染，服务端无法抓取页面内容；内部 API 需登录 Cookie 鉴权，不稳定。MVP 阶段改为用户手动粘贴笔记标题与互动数据，链接自动抓取留待后端完善后再做。

**用户流程**
1. 进入「账号诊断」Tab，查看诊断记录列表
2. 点击「新诊断」，弹出左右分栏弹窗
3. 左侧填写：账号定位（可选）+ 笔记标题与互动数据（每行一个标题，可附带点赞/收藏数，格式随意）
4. 点击「一键诊断」，左侧表单禁用，右侧实时流式输出诊断报告
5. 确认结果后点「保存到诊断记录」，弹窗关闭，列表新增一条记录
6. 点击列表中的记录，进入详情页查看完整报告

**输出物**
- **账号画像**：当前赛道、风格标签、整体数据表现
- **内容诊断**：表现好/差的选题类型、标题封面共性问题
- **优化建议**：赛道方向、可复用爆款结构、发布策略
- **选题推荐**：10 个贴合账号风格的具体选题

**需求优先级**

| 功能点 | 优先级 |
| --- | --- |
| 手动粘贴标题数据 + 诊断报告 | P0 |
| 诊断记录列表 + 详情页 | P0 |
| 链接自动抓取 | 暂不做（依赖后端） |

### 4.4 场景三：单篇文案生成

## 5. 技术方案

### 5.1 架构

```
┌────────────────┐         ┌──────────────────────┐
│  浏览器（用户）  │ ──────> │ Cloudflare Workers    │
│  纯静态 Web     │ HTTPS   │ (Serverless)          │
│  (Next.js)      │         │  - 小红书爬取代理      │
│                 │         │  - Claude API 代理     │
└────────────────┘         │  - 鉴权 + 计费         │
                            └──────────────────────┘
                                      │
                        ┌─────────────┼─────────────┐
                        ▼                           ▼
                 小红书公开页面                Claude API
                 (m.xiaohongshu.com)         (Anthropic)
```

### 5.2 技术栈

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Next.js + React + TailwindCSS | 部署到 Cloudflare Pages（免费） |
| 后端 | Cloudflare Workers | 每天 10 万次请求免费 |
| 数据库 | Cloudflare D1（SQLite） | 免费额度 5GB |
| 鉴权 | Clerk / 自建 JWT | 用户体系 |
| 支付 | 微信支付 / 支付宝（付费用户侧主力） | |
| 模型 | Claude（claude-sonnet-4-6） | 通过官方 API |

**关键点**：整套架构在用户量 < 5000 日活时，Cloudflare 完全免费。

### 5.3 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 前端交互 < 500 ms；模型响应流式输出，首字 < 3s |
| 兼容 | Chrome / Edge / Safari 最新两版，**仅桌面端**，不做移动端适配 |
| 安全 | 用户生成内容仅与账号绑定，API Key 仅服务端持有 |
| 可用性 | MVP 阶段不追求 SLA，提供"稍后重试"兜底 |

### 5.4 小红书内容获取（关键实现）

**方案**：Cloudflare Workers 作为代理，访问小红书 Web 端（m.xiaohongshu.com）解析 HTML/JSON。

**潜在风险与应对**：
- **反爬**：小红书有频率限制、Referer 校验、部分数据需登录。
  - 应对：使用 Worker 的多 IP 出口 + 合理频控；必要时接入低成本第三方数据服务（如新榜 API）兜底。
- **页面结构变动**：小红书改版可能导致解析失败。
  - 应对：抓取逻辑与业务逻辑解耦，Workers 上热更新即可修复，不影响前端。
- **合规**：见 §7 免责声明。
